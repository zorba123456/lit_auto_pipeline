## 1. 服务概览（纠正后）

这是一个运行在 **腾讯 ima 知识库** 上的 **垂直共享知识库**（案例名：「医美文献」），不是腾讯为医美单独做的行业产品。

| 维度 | 实测/可见事实 |
|------|---------------|
| 产品载体 | **ima 知识库**（腾讯通用 AI 知识管理产品） |
| 内容 | 大量 **英文期刊 PDF 全文**，按文件夹（如「医美文献」）组织 |
| 主界面交互 | **标题列表 → 点击 → 弹窗/分屏看 PDF 原文**；列表层 **没有** AI 摘要或解读 |
| 核心 AI 入口 | 底部 **「基于知识库提问」**：对库内语料做 **RAG 式问答** |
| 规模（截图） | 约 **21,717** 条、**3,682** 成员（创建者维护的共享库） |
| 推广 | **微信群** 为主（邀请加入知识库 / 传播链接），而非应用商店或官方行业频道 |

**本质**：运营者把海量 PDF 灌进 ima 共享库 → 成员加入后可 **读全文 + 对全文语料提问**；AI 价值集中在 **库级问答**，而非 **逐篇预制解读 feed**。

## 2. 产品架构（围绕 ima 知识库，非脑补）

```
┌─────────────────────────────────────────────────────────────┐
│  推广层：微信群（邀请链接 / 二维码 / 口令）                    │
│    · 拉新、续订、答疑；无独立「解读流」产品层                   │
├─────────────────────────────────────────────────────────────┤
│  腾讯 ima 知识库（平台能力）                                  │
│    · 多格式上传与解析（PDF 等）                               │
│    · 共享知识库 + 成员订阅                                    │
│    · 文件列表 / 预览 / 导出（右键 Save As 等）                │
├─────────────────────────────────────────────────────────────┤
│  用户主路径（实测）                                           │
│    ① 打开「医美文献」文件夹                                   │
│    ② 浏览英文标题列表                                         │
│    ③ 点击 → 阅读 PDF 原文（无列表层 AI 解读）                  │
│    ④ 底部「基于知识库提问」→ 跨库自然语言检索/问答             │
├─────────────────────────────────────────────────────────────┤
│  可选能力（平台级，本库是否常用待观察）                        │
│    · 单篇 PDF 打开后：元宝 Summary 等（非列表流）              │
│    · ima 2.0：AI 要点、任务模式（报告/播客）— 通用功能         │
└─────────────────────────────────────────────────────────────┘
```

### 2.1 「基于知识库提问」— 真正的产品核心

这是 **ima 的标准能力**，在本案例中被 **2 万+ 篇 PDF** 放大：

| 环节 | 行为 |
|------|------|
| 入库 | 运营者（或协作者）持续上传 PDF；平台做解析、分块、索引 |
| 阅读 | 用户仍以 **直接读 PDF** 为主；列表不提供预制 AI 内容 |
| 提问 | 用户在底部输入自然语言问题；系统从 **库内全文语料** 检索相关片段，再由大模型生成回答 |
| 价值 | 「我不必读完 2 万篇，但可以问跨文献问题」— **检索 + 生成**，不是 **编辑精选 + 单篇导读** |

**与 RSS / 阅读器差异**：没有「每篇条目自带摘要」的消费习惯；**AI 是库上的统一接口**，不是每篇文章的包装层。

### 2.2 微信群推广 — 增长与合规的双重含义

| 方面 | 说明 |
|------|------|
| 为何用群 | 医美从业者已在微信生态；群适合 **信任背书 + 即时通知**（新文献入库、库链接更新） |
| 转化路径 | 群内发 ima 知识库邀请 → 用户加入成为成员 → 获得全文阅读与提问权限 |
| 产品含义 | **社群运营 + 平台工具** 的组合；腾讯提供 **容器与 AI**，运营者提供 **语料与人力** |
| 合规含义 | 群 + 公众号若 **公开宣传**「万篇全文 PDF 免费读」，会放大 **传播范围** 与 **主观恶意/营利** 的认定风险（见 §5） |

## 3. 能力评估（基于实测）

### 3.1 对该运营模式的客观优势

| 能力 | 说明 |
|------|------|
| 极低使用门槛 | 加群 → 加库 → 立刻拥有大规模语料与 RAG |
| 微信闭环 | 文件可从微信导入 ima；推广不在腾讯外另建渠道 |
| 库级 AI 一次建设 | 不必为每篇 PDF 跑 RPA 生成导读；上传即可被问答索引 |
| 网络效应 | 成员数（3,682）本身就是信任与壁垒 |
| 阅读体验简单 | 标题 → PDF，无信息过载 |

### 3.2 局限（产品层，非法律层）

| 问题 | 说明 |
|------|------|
| 列表无结构化元信息 | 英文标题为主；难看到期刊、DOI、期数、作者（对比 AES CNKI 结构化 description） |
| 无编辑筛选可见性 | 用户不知道「为何入库 / 为何值得读」 |
| 无标签订阅 | 加入 = 全库；无法「只订隆鼻」 |
| RAG 黑盒 | 答句是否引用原文、引用哪一段，实测界面未强调可审计性 |
| 数据不可导出 | 锁定 ima + 腾讯云；难以迁移到自有 XML/Zotero 管线 |
| 依赖运营者 | 库质量、更新频率、是否删改，全看创建者 |

### 3.3 与 AES-INTEL 对比（纠正后）

| 维度 | ima「医美文献」共享库 | AES-INTEL（已定方案，见 §4） |
|------|----------------------|------------------------------|
| 核心消费 | **PDF 全文 + 库级提问** | **标签订阅流 → 中间页**（元信息 + 摘要 + AI 导读） |
| AI 形态 | 底部 **库级 RAG**（「基于知识库提问」） | **单篇「AI 阅读」** = 豆包分享外链；**不做** 库级 RAG |
| 全文在哪 | 2 万+ PDF **集中在 ima 共享库**，成员直接读 | **AES 不托管 PDF**；全文在 **豆包分享会话** 内，用户 **用自己豆包账号** 继续问答 |
| 列表层 | 标题 → PDF | 结构化元信息、标签 → 中间页 |
| 中文 | 本库以英文 PDF 为主 | CNKI/CMA 分轨；中文 MVP **无 AI 阅读**（C15） |
| 合规策略 | 全文共享库（见 §5 风险） | 不建 mega 全文库；中间页链 DOI/官方源；AI 阅读仅英文外链 |
| 推广 | 微信群 | RSS/PWA；可选微信入流（C23） |
| 筛选 | 运营者黑盒 | 编辑打标 + `ai_curator`（C16–C21） |

**结论**：ima 是 **「集中式全文库 + 库级 RAG」**；AES 是 **「编辑精选流 + 中间页导读 + 单篇豆包外链」** — 两者 AI 路径 **不同**，不是同一产品的两种皮肤。

## 4. AES 已定方案：「AI 阅读」= 豆包分享链接

> **讨论结论（2026-06-22）**：英文文献的 **「AI 阅读」** 不是自建 RAG、不是托管 PDF 库，而是 **编辑后台跑豆包 RPA 产出的分享链接**（`doubao_read_url`，UI 文案「AI 阅读」，见 C14/C30）。

### 4.1 用户侧体验

```
标签订阅流 → 点条目 → 英文中间页
  ├─ 元信息（期刊、DOI、作者…）+ 英文摘要
  ├─ AI 导读（`ai_summary_zh`，编辑侧 Worker 注入 XML）
  ├─ 原文链接（`publisher_url` → 期刊/DOI 官方页）
  └─ 【AI 阅读】→ 跳转豆包分享链接
        · 链接内已含该篇 **全文 PDF** 及 **首轮 AI 对话/导读**
        · 用户打开后 **登录自己的豆包账号**，可 **继续对该 PDF 提问**
        · 后续问答发生在 **豆包侧**，不在 AES Reader 内
```

**Reader 不展示 PDF 文件**（C14）；用户若要「读全文 + 问 AI」，走 **AI 阅读外链**，而非在 AES 内嵌阅读器或共享库中翻 PDF。

### 4.2 编辑侧 / 技术链（Route 2）

```
编辑取得 PDF（合法来源）→ data/pending/
  → batch_worker + doubao_rpa.py（单篇队列，2–5 分钟间隔）
  → 产出：中文 AI 导读 + doubao 分享链接
  → 注入 XML / entries 表（ai_summary_zh + doubao_read_url）
  → 用户刷新中间页即可见
```

详见 [`AES_PIPELINE_HANDOFF.md`](../AES_PIPELINE_HANDOFF.md)：`doubao_rpa.py` 已通过 Share API 稳定提取分享链接。

### 4.3 与 ima「基于知识库提问」的本质区别

| | ima 竞品 | AES「AI 阅读」 |
|--|---------|----------------|
| AI 接口 | **一个库、一个输入框**，跨 2 万篇 RAG | **每篇一条豆包分享链**，单篇会话 |
| 语料组织 | 运营者 **批量灌库** | 编辑 **逐篇加工** 后才出现 AI 阅读入口 |
| 用户账号 | ima 成员身份 | **用户自己的豆包账号** 继续问答 |
| AES 是否存全文 | — | **不存**；仅后台加工时临时喂给豆包 |
| 跨文献提问 | ✅ 库级天然支持 | ❌ MVP **不做**；单链仅该篇 PDF |
| 中文 | — | **不提供 AI 阅读**（C15） |

**一句话**：ima 的 AI = **「整个硬盘一起问」**；AES 的 AI 阅读 = **「这篇值得读，点开去豆包接着问」**。

### 4.4 合规边界（相对 ima 的差异，非法律意见）

| 风险点 | ima 模式 | AES 豆包链模式 |
|--------|---------|----------------|
| 集中全文库 | 2 万+ PDF 对 3600+ 成员 **可浏览/可导出** | **无** 用户可逛的全文库 |
| 传播形态 | 一个知识库邀请 = 全部文献 | **逐篇** 中间页 URL；豆包链 **按篇** 生成 |
| PDF 仍上云 | PDF 在 ima/腾讯 | 加工时 PDF 上传 **豆包**；用户侧为 **外链跳转** |
| 剩余风险 | — | 分享链是否可被未授权扩散、豆包链有效期 — **待产品观察** |

AES **仍拒绝** ima 式 mega 库；豆包链是 **在精选 + 单篇加工** 前提下提供的 **英文增强能力**，不是对标 ima 的库级 RAG 替代品。

### 4.5 侵权风险：比 ima 低吗？能接受吗？（产品结论）

> **非法律意见**；供团队是否采用「AI 阅读 = 豆包链」方案决策用。

#### 相对 ima：**明显更低**（多维度）

| 维度 | ima 共享库 | AES 豆包链 | 对风险的影响 |
|------|-----------|-----------|-------------|
| 传播形态 | 一次加入 ≈ **2 万篇全文** | **逐篇** 中间页 + 单条豆包链 | ima 更像「批量向公众提供」 |
| AES 是否存全文 | — | **不存**；用户侧无 PDF 库 | 降低 AES 作为「内容分发站」形象 |
| 可浏览/导出 | 列表点读、Save As | Reader **无 PDF**；仅外链 | ima 证据链更完整 |
| 库级 RAG | 全文 **解析索引** 供万人问 | **无** 库级索引 | ima 多一层「复制+利用」 |
| 规模 | 万篇 × 数千人 | **编辑精选** 篇数（量级可控） | 投诉与曝光面更小 |
| 中文 | — | **不做 AI 阅读**（C15） | 知网版权更敏感，主动回避 |
| 主路径 | 直接读库内 PDF | **DOI/官方链** 为主；豆包为 **增强** | 合规叙事可站住 |

**产品判断**：在「PDF 来源同样未授权」的假设下，豆包链方案在 **传播范围、集中存储、可审计性** 上均弱于 ima，**相对风险显著更低** — 这是 **量级与架构差异**，不是「换平台就合法」。

#### 绝对风险：**不是零**，不能叫「安全」

| 仍存在的风险 | 说明 |
|-------------|------|
| **复制** | 编辑侧仍要把 PDF **上传豆包** 加工 → 仍可能构成复制 |
| **向公众提供** | 分享链若可被 **未登录/转发** 打开，仍可能被视为向他人提供全文 |
| **AI 导读** | `ai_summary_zh` 基于全文生成 → 可能有 **衍生利用** 争议（通常低于全文库） |
| **规模累积** | 若每周大量加工 **付费墙** PDF 并挂链，风险 **随篇数上升** |
| **平台政策** | 豆包链失效、账号封禁、出版商向豆包/AES 投诉 — **技术依赖风险** |
| **来源** | OA / 机构订阅 / 编辑合法持有 vs Sci-Hub 式 PDF — **来源决定上限** |

**关键**：豆包链 **不等于**「只链 DOI 就不侵权」；它只是 **不像 ima 那样经营一个公开全文仓库**。

#### 「能接受吗？」— 建议的产品立场

| 结论 | 内容 |
|------|------|
| **相对 ima** | ✅ **可接受采用** — 架构上刻意错位，风险 **显著低于** ima 模式 |
| **绝对合规** | ⚠️ **有条件接受** — 不是零风险；需 **运营约束** 而非仅靠产品设计 |
| **不可接受** | ❌ 把「比 ima 低」理解成「随便传 PDF 都合法」 |

**建议写入产品原则的约束（降低绝对风险）**：

1. **优先加工 OA 或编辑已合法取得的 PDF**；无 PDF 时中间页仍可用（仅摘要 + DOI），**不挂 AI 阅读**。
2. **AI 阅读为增强、非默认**：中间页 **原文官方链** 始终可见且优先；豆包链标注「需登录豆包 / 由第三方提供」。
3. **不批量推广豆包链**：微信群等只发 **中间页 URL**，不打包链、不宣传「全文免费库」。
4. **控制加工规模**：精选流，非全量期刊 mirror。
5. **中文坚持 C15**：不提供 AI 阅读。
6. **投诉响应**：收到下架要求 → 撤链 + 撤导读，保留元信息与 DOI。
7. **待核实**：豆包分享链 **有效期、是否需登录、转发是否带 PDF** — 影响风险评级，需实测记录。

**团队可记录的决议（建议）**：

> 在遵守上述约束的前提下，**「AI 阅读 = 豆包分享链」的侵权风险显著低于 ima 式全文共享库，产品层面可接受**；绝对风险仍为 **中低灰度**（视 PDF 来源而定），**不等于法律背书**，重大决策前仍建议法务过一遍。

### 4.6 团队决议（v1.4 · 培育期）

| 项 | 结论 |
|----|------|
| **决策** | **先用豆包链** 作为英文「AI 阅读」实现 |
| **首要理由** | **用户体验流畅** — 中间页一点进豆包即可读全文并继续问答，无需自建 PDF 库或 RAG |
| **风险态度** | **已知非零风险，培育期接受**；仍遵守 §4.5 运营约束，**不做** ima 式 mega 库 |
| **商业阶段** | **培育期无收费、无盈利动作** — 降低「营利性传播」情节；不代表未来可默许放大规模 |
| **迭代策略** | **先用，后看** — 运行中观察豆包链稳定性、投诉与访问控制；**后续若有更好方案再替换**（见下表） |
| **不变项** | 中文 **不提供 AI 阅读**（C15）；Reader **不托管 PDF**；DOI/官方链保留 |

**后续可迭代方向（待观察，非承诺）**：

| 方向 | 说明 |
|------|------|
| 仅 DOI + 用户自备 PDF | 中间页导读 + 官方链；用户自行上传 AI | **AES 侧零风险** |
| 出版商 / OA 正式授权 | 合作后的合法全文路径 | 视授权而定 |
| 机构订阅 deep link | 链到用户本单位图书馆 | **零**（AES 不传 PDF） |
| 摘要级 AI、不挂全文链 | 仅用 RSS 摘要做导读 | **零**（若不加工全文 PDF） |
| 其他第三方阅读 AI | 若豆包政策或链能力恶化，评估替代 RPA/API |

**记录用语（对外/对内一致）**：英文 AI 阅读 = **豆包分享外链（培育期方案，UX 优先）**，非永久架构承诺。

### 4.7 若要「更低风险」：邮件匿名 vs 豆包链 · 能否设计同样流畅？

> **风险边界（AES 运营方视角）**  
> - 只要 AES **主动把 PDF 交给用户**（豆包链、微信文件、邮件附件…），AES 侧 risk **非零**。  
> - **仅 DOI + 导读，PDF 由用户自己合法取得并自行上传 AI** → 对 AES 为 **零**（不传复制件、不提供全文获取路径）。  
> - 下文「零 / 中低 / 中 / 高」均指 **AES 平台责任档位**，非用户个人使用行为。

#### 风险档位（产品讨论用 · v1.6 修正）

```
  高   ████████████████████  ima 万篇共享库 + 库级 RAG + 公开拉新
  中   ████████░░░░░░░░░░░░  豆包 **分享链**（培育期方案；链可能被转发？待核实）
  中低 ██████░░░░░░░░░░░░░░  **绑定用户** 私有投递（微信私发 PDF、邮件附件、一次性鉴权下载）
  —    （无「低」档：凡 AES 触达 PDF 全文，至少中低以上）
  零   ░░░░░░░░░░░░░░░░░░░░  **仅 DOI + 导读**；用户 **自备 PDF** 上传豆包/ChatGPT（AES 不传全文）
```

**邮件匿名发全文** 仍在 **中低**，不是零：AES 仍在 **发复制件**。

| 邮件方案 | AES 风险档 | UX |
|----------|-----------|-----|
| 匿名邮箱发 PDF 附件 | 中低 | ❌ 差 |
| 邮件里只放 DOI | **零** | ✅ 简单；无 AES 侧全文 AI |
| 一次性私有下载链 | 中低 | 中 |

**结论**：要 **AES 侧零风险**，只有 **不传 PDF** 一条路；邮件发附件 **不能** 达到零。

#### 目标形态（修订）：流畅 vs 零风险 的张力

**零风险（方案 D）** — AES 不碰 PDF：

```
中间页：AI 导读 + DOI 官方链 + 【在豆包中阅读】
  → 打开豆包 **空白对话 / 预制提示词**
  → 用户 **自己** 从 DOI/机构库拿到 PDF 并上传
  → 后续问答全在用户 ↔ 豆包之间
```

**非零但想更流畅** — 只能走 **私有投递**，不能走「公共分享链」：

```
中间页点【发到我的微信】→ 微信私聊收 PDF → 用户用豆包打开（方案 B）
```

~~**方案 E**（代投用户豆包私有会话）~~ → **基本不可行，搁置**（见下）。

#### 可行设计方向（v1.6）

| 方案 | AES 风险 | UX | 状态 |
|------|---------|-----|------|
| **A. 豆包分享链** | 中 | ★★★★★ | ✅ **培育期采用** |
| **B. 微信私发 PDF** | 中低 | ★★★★ | 📋 下一档 **唯一值得验证** 的降链方案 |
| **C. 邮件附件** | 中低 | ★★ | 备用通道 only |
| **D. DOI + 用户自备 PDF** | **零** | ★★★ | 📋 **合规底线 / 收紧时默认** |
| ~~**E. 豆包代投用户账号**~~ | — | — | ❌ **搁置**：无公开 API/OAuth；RPA 登用户号不可接受；**短期无路径** |
| **F. 浏览器插件帮上传** | **零**（AES 不传文件） | ★★★ | 远期；用户本机已有 PDF |
| **G. 一次性鉴权下载** | 中低 | ★★★ | 可选；AES 仍短暂托管副本 |

**方案 E 搁置理由**：豆包未提供「第三方代传 PDF 至指定用户私有会话」的可靠接口；幻想与分享链 UX 等同的「静默投进用户账号」**现阶段不成立**。迭代 **只盯 B**，不投 E。

#### 培育期后验证（修订）

**仅方案 B · 微信私发 PDF**：

- 中间页 **「发送到我的微信」**（需绑定 OpenID）  
- 无公开 URL；1 次点击 + 微信内打开豆包 ≈ 接近 A 的流畅度  
- 仍 **非零**，但弱于分享链的「可转发」特征  

**零风险对照**：同期保留 **方案 D** 入口（DOI +「复制提示词 → 自备 PDF 上传豆包」），供敏感篇或投诉后降级。

#### 与当前决议的关系（v1.6）

| 阶段 | 全文路径 | AES 风险 |
|------|----------|----------|
| **现在（培育期）** | 豆包分享链（A） | 中 |
| **下一档** | 微信私发 PDF（B） | 中低 |
| **合规底线 / 收紧** | DOI + 用户自备 PDF（D） | **零** |
| **搁置** | 豆包代投用户账号（E） | — |
| **不推荐主路径** | 邮件（C） | 中低 |

**讨论记录**：「完全隔绝 **AES 侧** 风险」**可以** — 即 **方案 D**；代价是 UX 降档。**不能** 既要 AES 传全文又要声称零风险。

### 4.8 全球最佳实践 · 脑洞库（不受 §4.7 A–G 限制）

> **目的**：跳出「豆包链 / 微信发文件 / 邮件」框架，从 **国际学界与商业产品** 归纳 **合法全文 + AI** 的通行做法，供 AES 长期架构参考。  
> **行业共识**（ALA / 图书馆技术报告）：**Access Broker 浏览器插件**（Unpaywall、LibKey Nomad 等）是便利工具，但 **SeamlessAccess / GetFTR** 代表的 **「用用户已有权利读合法副本」** 才是正道；**平台不应托管未授权 PDF 库**（ima 反例）。

#### 全球「正统」范式一览

| 范式 | 代表产品 | 核心机制 | AES 侧风险 | UX |
|------|----------|----------|-----------|-----|
| **合法 OA 解析** | [Unpaywall](https://unpaywall.org)、[OpenAlex](https://openalex.org)、[ICanHazPDF](https://github.com/hugo-alves/icanhazpdf) | DOI → 查 **作者自存档 / PMC / 机构库** 的 **合法免费 PDF URL** | **零**（只链出去） | ★★★★ 一键若命中 OA |
| **机构 entitlement** | [LibKey Nomad](https://thirdiron.com/libkey-nomad/)、[GetFTR](https://www.getftr.org/)、[SeamlessAccess](https://seamlessaccess.org/) | 用户 **机构 SSO** → 用 **本单位已订** 的刊读 PDF | **零** | ★★★★★ 有订阅时极顺 |
| **第三方合法全文 + AI** | [Semantic Scholar](https://www.semanticscholar.org) Ask This Paper、[Semantic Reader](https://www.semanticscholar.org/product/reader) | **S2 合法索引** 的 OA 全文上做 AI；付费篇链出版商 / GetFTR | **零**（链出或 API 用 OA 语料） | ★★★★ |
| **用户自有文献库** | [Zotero](https://www.zotero.org)、[ReadCube Papers](https://www.papersapp.com)、[NotebookLM](https://notebooklm.google.com) | PDF 在 **用户本地/云**；产品只索引 **用户已导入** 的文件 | **零** | ★★★ 需用户先攒库 |
| **按篇合法租借** | [DeepDyve](https://www.deepdyve.com) | **$/篇租用** 浏览器内读（非盗版）；企业版团队合规 | **零**（商业授权） | ★★★★ 付费但确定合法 |
| **出版商原生** | Springer Nature / Elsevier 实验性 AI Reader | 在 **出版商站点** 内读+AI | **零** | ★★★ 依赖各刊 |
| **证据合成（无全文）** | [Elicit](https://elicit.com)、[Consensus](https://consensus.app) | AI 主要在 **摘要/元数据** 层做综述 | **零** | ★★★ 非逐篇深读 |
| **集中共享库 + RAG** | ima、NotebookLM 团队版 | 运营者灌 PDF | **高~中** | ★★★★★ ima 已验证 |

**启示**：世界一流产品的 **默认假设** 是 — **AES 不拥有 PDF**；全文来自 **OA、用户订阅、用户硬盘、或付费渠道**。

---

#### 脑洞方案（按创新度分组）

##### Ⅰ. 「Access Broker」— 最贴近全球最佳实践（推荐长期主方向）

**S1 · 中间页 + Unpaywall / OpenAlex OA 按钮**

```
中间页 DOI
  → 调用 Unpaywall API（仅需 email 标识）
  → 若 is_oa：显示【免费阅读合法 PDF】→ 出版社或 PMC 链接
  → 若无 OA：显示 DOI + 机构登录提示 + DeepDyve 租借链
```

- AES **零托管**；医美英文文献中 **NIH/PMC 绿路** 可覆盖部分篇（整形/修复相关）。  
- 可叠加 **「用豆包打开此 OA 链接」** 预制提示词 — 用户 **自己** 在豆包粘贴 URL 或上传刚合法下载的 PDF。

**S2 · 浏览器插件「AES Lens」（对标 LibKey Nomad）**

- 用户装插件 + **可选** 绑定机构（医院图书馆 OpenAthens / VPN 说明）。  
- 在 AES 中间页、PubMed、Google Scholar 上：自动 badge **「合法 PDF 可用」**。  
- 插件 **在用户浏览器内** 完成跳转 — AES 服务器 **不碰 PDF**。  
- 中国痛点：很多医美医生 **有机构订阅但不会用** — 插件价值是 **教路径** 而非发文件。

**S3 · GetFTR / 机构 SSO 深链（Semantic Scholar 同款）**

- 中间页按钮：**「通过机构访问」** → SeamlessAccess 登录 → 出版商 PDF。  
- 适合 **三甲教学医院** 用户；AES 做 **导流 + 导读**，不做仓储。  
- 中国区落地需调研：多少目标用户有可用的 **eduGAIN / 医院图书馆远程访问**。

##### Ⅱ. 「AI 在合法第三方」— AES 不做全文 AI

**S4 · 外链 Semantic Scholar「Ask This Paper」**

- 中间页：**「在 Semantic Scholar 向本篇提问」** — 跳 S2 已有 **OA 全文** 的页面。  
- AES 保留 **中文导读 + 标签**；深读交给 **Allen Institute** 的合法基础设施。  
- 限制：仅部分篇有 Ask This Paper；非 OA 仍无解。

**S5 · 分轨：OA 篇链 S2 / 非 OA 篇链 DOI 或 DeepDyve**

| 篇类型 | AI 阅读入口 |
|--------|------------|
| Unpaywall 命中 OA | S2 Ask This Paper 或 OA PDF + 用户自备豆包 |
| 机构 entitlement | GetFTR / LibKey 流程 |
| 其余 | DeepDyve 租借（~$1/24h 级）或出版商 PPV |
| 培育期兜底 | 豆包链（团队已定，非长期正途） |

**S6 · Elicit / Consensus 式「证据卡」**

- 不做全文 AI 阅读，做 **PICO / 结论 / 证据等级** 卡片（AES 导读的升级版）。  
- 用户要深读再点 DOI — **零全文风险**，适合 **筛选流** 定位。

##### Ⅲ. 「用户文献在用户手里」— 零风险 + 可做出 ima 级 RAG

**S7 · 连接用户 Zotero / 本地文件夹**

- 用户授权 AES 读 **仅 metadata** 或 **用户自选** 的 Zotero 集合。  
- **RAG 跑在用户自己的 PDF 上**（本地插件或用户自建 Obsidian/ima）— AES 只推 **「值得加入 Zotero」** 的精选条目。  
- 与项目已有 **Zotero 协作** 方向（`aes_workbench_design.md` §18）一致。

**S8 · 「我的云盘里的医美 PDF」**

- 用户绑 **个人 Google Drive / 坚果云 / 微信文件助手转存** — AES **索引用户自有文件** 做个人 RAG（类似 ima，但 **库是用户的**）。  
- 法律叙事：**用户对自己的文件提问**；AES 是工具不传播。  
- 冷启动难，但 **零 AES 分发风险**。

**S9 · NotebookLM 式「导入包」**

- 中间页生成 **`.enw` / BibTeX + 导读 + OA PDF URL 列表** 一键导入用户 NotebookLM/ima **私有库**。  
- 一步手动，但 **完全用户侧** 持有全文。

##### Ⅳ. 「商业合法全文」— 可收费阶段的正路

**S10 · DeepDyve / Reprints Desk 企业通道**

- 中间页：**「合法租借全文 ¥X/篇」** → DeepDyve 24h 流式阅读 + 用户自行复制要点。  
- 企业版有 **版权 cleared** 叙事；适合未来 **机构付费** 而非 AES 散播 PDF。  
- 与「培育期无盈利」不冲突 — 用户 **向 DeepDyve 付费**，AES 收 **导流/订阅** 而非卖盗版。

**S11 · 出版商 / 学会合作包**

- 与 **ISAPS、ASPS、Aesthetic Surgery Journal** 等谈 **策展 RSS + 官方 AI 阅读 iframe/API**。  
- 长期 **唯一** 能同时 **零风险 + 极致 UX** 的路径 — 慢，值得并行商务接触。

##### Ⅴ.  wildcards（脑洞但不排除）

| 编号 | 想法 | 备注 |
|------|------|------|
| S12 | **PMC HTML 全文内嵌**（非 PDF） | 生物医学 OA 篇可读 HTML；AES iframe 链 PMC（须遵守 PMC 条款） |
| S13 | **预印本优先** | medRxiv/bioRxiv 全文合法；医美外科预印本少，作补充源 |
| S14 | **音频导读 + DOI** | 播客式中文解读（ima 2.0 任务模式），**不碰 PDF** |
| S15 | **QR → 医院图书馆移动门户** | 线下会场景：扫 QR 用 **医院 IP/VPN** 打开 DOI |
| S16 | **AI 只读「允许摘要扩展」** | CrossRef / PubMed abstract + 编辑撰写扩展；全文一律外链 |
| S17 | **联盟采购 OA 转换费** | 帮作者/机构付 **Open Access fee** 换永久合法链 — 重运营 |

#### 对 AES 的「北极星」建议（讨论用，非已定）

| 层级 | 策略 |
|------|------|
| **长期正途** | **Access Broker 组合**：Unpaywall OA 按钮 + 机构访问引导 +（可选）DeepDyve 租借 + 中文导读留在 AES |
| **AI 深读** | **能 outsource 就 outsource**：OA 篇 → Semantic Scholar；其余 → 用户 entitlement 或自备 PDF 进豆包 |
| **培育期** | **豆包链兜底**（已定）— 明确标注 **过渡方案** |
| **不做** | ima 式万篇库；Sci-Hub 式源；假装「只链 DOI」却 secretly 批量托管 |

**中国医美用户特殊点**：

- 英文刊 **OA 比例低于 CS/生物**，但 **PMC / 作者自存档** 仍值得每篇自动查。  
- **机构订阅浪费** 是真实痛点 — **S2 插件 + 图书馆 VPN 教程** 可能比发 PDF 更有价值。  
- 微信生态：**S9 导入包 / 链 OA URL** 比 **S8 用户云盘** 更易落地。

#### 可立刻做的低成本验证（P2 调研）

1. 抽 AES 现有英文条目 **100 篇**，跑 Unpaywall API → 统计 **OA 命中率**。  
2. 命中 OA 的篇，测 Semantic Scholar 是否已有 **Ask This Paper**。  
3. 调研 **DeepDyve** 对 *Aesthetic Surgery Journal*、*Plast Reconstr Surg* 等 **覆盖率**。  
4. 画一版中间页 **wireframe**：主按钮 **「合法全文」**（OA/机构），次按钮 **「AI 阅读·豆包」**（培育期）。

**讨论点 8（待决）**：长期是否将 **「合法全文解析（S1）」** 升为中间页 **默认主按钮**，豆包链降为 **兜底**？

### 4.9 硬约束：多数新文献合法全文需付费 · 平台不能代付（v1.8）

> **团队结论（2026-06-22）**：医美 **新** 英文文献 **绝大多数在付费墙后**；合法读全文 = **用户自己付钱**（或走已付费的机构订阅）。**AES 不可能、也不应替用户批量付费** — 这绕不开，也解释了 ima 类「免费万篇库」为何存在（本质在替用户承担/规避获取成本）。

#### 合法路径按「谁付钱」分类

| 路径 | 谁付 | 覆盖医美新文献 | AES 能做什么 | AES 不能做什么 |
|------|------|----------------|-------------|----------------|
| **OA / PMC / 自存档** | 已预付（APC 等） | **少数** 新篇 | Unpaywall 按钮链出 | 变付费为免费 |
| **机构订阅** | 医院/大学已订 | **部分**（用户会用才行） | 教 VPN/SSO、插件引导 | 替无机构用户订阅 |
| **出版商 PPV** | **用户** ~$30–50/篇 | **多数** 新篇 | 链到 DOI 购买页 | **代付** |
| **DeepDyve 租借** | **用户** ~$1/24h | 视刊覆盖 | 深链到 DeepDyve | **代付** |
| **豆包链（培育期）** | AES 编辑侧加工成本 | **高**（若编辑有 PDF） | 提供 UX | 声称合法免检 |
| **ima 式共享库** | 运营者承担风险 | **高** | — | AES **不做** |

**结论**：对 **多数付费新篇**，「合法」与「免费全文」**不可同时满足**；Access Broker 能做的是 **帮用户找到最省钱的合法入口**，不是 **消灭付费**。

#### 修正后的产品三角（医美新文献）

```
                    合法
                   /    \
                  /      \
           免费全文        付费全文
          （少数 OA）      （大多数新篇）
                \          /
                 \        /
                  流畅读+AI
                       ↑
              豆包链 / ima 填这个洞
              但 AES 不能长期靠侵权填洞
              也不能平台代付填洞
```

**AES 能长期站住的位置**：

1. **筛选 + 中文导读**（摘要/元数据层）— **零风险、零代付**，价值不依赖全文。  
2. **合法全文入口** — 链 DOI 购买 / DeepDyve / 机构访问；**钱用户出**，AES 只导流。  
3. **AI 深读** — 合法侧只有：**用户付完钱拿到 PDF 后自己上传豆包**（零 AES 风险），或 **培育期豆包链**（非零）。  
4. **不承诺**「篇篇免费合法全文」— 与 ima 差异化是 **诚实 + 精选**，不是 **_magic 免费库**。

#### 对 §4.8「北极星」的修正

| 原表述 | 修正 |
|--------|------|
| Access Broker 为长期主方向 | **仍对**，但主价值是 **OA 少数篇 + 机构引导**；对 **多数付费新篇** 主按钮只能是 **「出版商购买 / 租借」** |
| Unpaywall 升主按钮 | **仅对 OA 命中篇** 显示「免费阅读」；未命中则 **主按钮 = DOI 购买**，次按钮 = 机构/DeepDyve |
| DeepDyve | **用户自费** 的合法选项之一，AES **不补贴** |
| 豆包链 | 培育期填 **「付费墙 + 平台不代付 + 用户仍要读」** 的 UX 洞；**不是**合法替代，是 **商业现实下的过渡** |

#### 中间页按钮逻辑（建议 · 付费现实版）

```
每篇英文中间页：

① 【AI 导读】           ← AES 核心价值，始终有
② 【DOI / 期刊官网】    ← 多数新篇的 **合法主路径**（用户自购）
③ 【机构访问】          ← 有订阅的用户（可选）
④ 【DeepDyve 租借】     ← 愿小额付费的用户（可选，链出）
⑤ 【Unpaywall 免费 PDF】← **仅 API 命中 OA 时显示**
⑥ 【AI 阅读 · 豆包】    ← 培育期；标注过渡 / 非官方全文来源
```

**不对用户暗示**：AES 会提供免费合法全文库。

#### 与 ima 的再对比（付费视角）

| | ima | AES |
|--|-----|-----|
| 用户感知 | 「加库 = 免费读万篇」 | 「精选 + 导读；全文 **你自己买或机构读**；培育期有豆包增强」 |
| 谁承担获取成本 | 运营者（+侵权风险） | **用户或机构** |
| 平台代付 | 否（但隐性「免费送」） | **明确否** |

**讨论点 9（已定）**：**平台不替用户付文献费**；合法付费墙绕不开；豆包链是 **UX 过渡**，不是「合法方案赢了付费墙」。

### 4.10 证据链 vs 法律风险 — 「匿名邮件证据链没了？」（v1.9）

> **非法律意见**；区分两个常被混谈的维度。

#### 两个维度不要混为一谈

| 维度 | 问什么 | 匿名邮件发 PDF |
|------|--------|----------------|
| **A. 法律/合规风险** | 行为本身是否可能构成 unauthorized 复制、提供？ | **仍非零** — 仍在 **发全文复制件** |
| **B. 追责/证据风险** | 权利人 **能否较容易指认** 谁在做大规模传播？ | **相对豆包链/ima 可能更弱** — 见下表 |

**「证据链没有了」** 若指 **B 维度** — **部分成立，但远非「没有」**；若指 **A 维度** — **不成立**。

#### 与豆包链 / ima 的「证据链」对比（产品讨论）

| 渠道 | 相对易追溯的线索 | 传播面 |
|------|------------------|--------|
| **ima 共享库** | 创建者实名、成员 3682、库 ID、腾讯账号 | **大**、可批量投诉 |
| **豆包分享链** | 编辑 **实名豆包号**、分享 URL 可转发、腾讯侧日志 | 中（链可扩散） |
| **微信私发 PDF** | 服务号/企微主体、OpenID 绑定 | 小（一对一） |
| **匿名邮件附件** | 无品牌主页挂链；发件箱可伪装 | 小（一对一） |

**匿名邮件在 B 维度的可能优势**：

- 中间页 **不挂** 长期有效的公开 PDF URL  
- 发件人可 **与 AES 品牌/域名脱钩**（若运维与产品分离）  
- 无 **「万篇库 + 创建者名」** 式一键取证  

**但证据链 ≠ 零**：

- 邮件 **SMTP/服务商** 仍有 IP、时间戳、账号注册信息  
- **收件人** 持有邮件与附件，可配合投诉  
- PDF **元数据**、批次特征、发送规律  
- 若从 **AES 中间页触发**「发到邮箱」，产品/服务器侧仍有 **业务日志**  
- 司法机关 **调证邮箱服务商** 仍可能溯源 — 「匿名」多为 **提高成本**，非 **物理不可查**

#### 团队讨论结论（建议）

| 说法 | 判断 |
|------|------|
| 「匿名邮件 **基本隔离法律风险**」 | ❌ **不成立**（§4.7） |
| 「匿名邮件 **削弱公开传播的证据链**」 | ⚠️ **部分成立** — 相对 **实名豆包链 / ima** 在 **B 维度** 可能略好 |
| 「证据链没了就可以放心发」 | ❌ **过度推断** |
| **AES 产品立场** | **不以「切断证据链」为设计目标**；培育期已选 **豆包链（UX）**；邮件 **不升级** 为主路径 |

**与培育期豆包链的取舍**：豆包链 **实名、可转发** → B 维度往往 **更不利**；但 **UX 远胜** 邮件。若未来因 **B 维度** 收紧，优先 **微信私发（B）** 或 **DOI 自备（零）**，而非押注「匿名邮件 = 安全」。

---

1. **微信群作为触达** — 与 C23 一致；可推 **中间页 / 标签订阅**，**不推** PDF 包或全文库邀请。
2. **成员数 / 精选数作为信任信号** — AES 用「标签订阅数 / 本周精选篇数」替代 3,682 人同库。
3. **中间页一键到原文** — `publisher_url`（DOI/期刊）+ 可选「AI 阅读」豆包链，**两条路径分开**。

**明确不借鉴**：ima 库级 RAG、海量 PDF 共享库、公众号公开全文集。

## 6. 版权与合规讨论（ima 案例）

### 6.1 问题陈述

- 库内 **2 万+ 篇** 多为 **期刊论文 PDF 全文**。
- 成员 **3,682** 量级，远超个人学习「合理使用」常见规模。
- 通过 **微信群、公众号** 等公开或半公开渠道 **推广加入**，等于 **向不特定多数人提供获取全文的途径**。

**团队关切**：这是否 **严重侵权**？腾讯作为平台是否 **纵容**？

### 6.2 版权法层面（一般性原理，非个案法律意见）

| 要点 | 说明 |
|------|------|
| 权利归属 | 期刊论文 PDF 的著作权通常归属 **出版社 / 作者**（视转让协议而定），非上传者 |
| 典型禁止行为 | 未获授权 **复制、传播、向公众提供** 全文；大规模上传至共享库供数千人阅读，通常 **超出** 个人研究复制的合理边界 |
| 公开推广 | 公众号/群链接 **扩大传播范围**；若存在 **收费加入、广告、引流转化**，可能强化 **营利/恶意** 情节 |
| RAG 额外维度 | 平台对 PDF **解析、分块、索引** 用于问答，可能涉及 **复制件** 与 **衍生利用**；各国/各案认定不一，但 **不能** 视为「只存链接就不侵权」 |
| 「行业惯例」 | 医美圈私下传 PDF 常见，**常见 ≠ 合法** |

**倾向性判断（产品讨论用）**：若语料确为 **未授权期刊全文** 且 **大规模成员共享**，从合规角度看 **风险极高**，应假定为 **严重侵权风险**，而非「灰色可忽略」。

### 6.3 腾讯 / ima 的角色：纵容还是「平台中立」？

| 层面 | 分析 |
|------|------|
| 产品设计上 | ima **允许** 创建大型共享知识库、上传 PDF、成员订阅、库级问答 — 这是 **通用能力**，未限定医美或学术 |
| 平台是否「endorse」 | 未见腾讯 **官方** 为该「医美文献」库背书；更像是 **用户/运营者** 创建的内容 |
| 审核与责任 | 大型 UGC 平台通常采用 **事后通知-删除** 机制；**未主动下架 ≠ 法律上认可侵权**；也可能只是 **审核滞后或未触发投诉** |
| 是否「纵容」 | **主观意图无法替腾讯定性**；可观察事实：产品 **未** 在入库环节强制校验 DOI/出版商授权；**客观上降低了** 大规模传阅门槛 |
| 对比 AES | **不建** ima 式全文共享库；英文 **AI 阅读** = 豆包 **单篇外链**（用户自有账号问答）；中文 **无 AI 阅读**（C15）；中间页保留 **DOI/官方链** |

**讨论结论（建议写入产品原则）**：

1. **不要假设**「大厂产品里能跑，我们就安全」— 责任在 **内容提供者与运营者** 为主，平台规则随时可能收紧。
2. **不要对标** 其全文库模式；AES 坚持 **元数据 + 合法链接 + 编辑精选**。
3. 若未来有人 **投诉/下架**，ima 库可能 **整库不可用** — 依赖该模式的用户面临 **单点崩盘**；AES 自有 XML/Git 数据更抗平台政策变化。

### 6.4 公众号公开推广的特殊风险

| 行为 | 风险 |
|------|------|
| 公众号发文「万篇医美 PDF 免费读」 | 传播范围 **公开**、可截图取证；版权方 **通知-删除** 路径更短 |
| 附带 ima 邀请链接 | 将 **平台** 与 **侵权集合** 绑定；可能触发 **微信内容审核** 或 **出版社批量投诉** |
| 与「课件/资料分享」类比 | 正版课件亦需授权；**未授权期刊全文** 比培训课件 **更难** 主张合理使用 |

**待核实（非断言）**：需确认该库是否 **收费加入**、公众号主体是谁、是否有 **出版商合作** — 若有正式授权，风险模型 entirely 不同；**在无授权证据前，按高风险假设**。

### 6.5 豆包链 vs ima：风险层级（摘要 · v1.6）

```
侵权风险 — AES 运营方视角（产品讨论用，非法律排序）

  高   ████████████████████  ima：万篇共享库 + 库级 RAG + 群/号推广
  中   ████████░░░░░░░░░░░░  培育期豆包分享链
  中低 ██████░░░░░░░░░░░░░░  微信私发 PDF 等一对一投递（方案 B）
  零   ░░░░░░░░░░░░░░░░░░░░  仅 DOI + 导读，用户自备 PDF 上传 AI（方案 D）
```

AES 培育期选定 **中档（豆包链）**；**零档（D）** 为合规底线；**中低（B）** 为唯一规划的降档迭代。**方案 E 不纳入路线图。**

## 7. 讨论纪要

**议题**：ima 竞品实测 + AES「AI 阅读」方案 + 版权边界  
**日期**：2026-06-22  

---

### 讨论点 0：AES「AI 阅读」定义（已定）

| **决议** | **「AI 阅读」= 豆包分享链接**（`doubao_read_url`），内含全文 PDF 及首轮对话；用户 **用自己豆包账号** 打开后继续问答 |
| **不是** | ima 式「基于知识库提问」、AES 内嵌 PDF 阅读器、AES 托管全文库 |
| **配合** | 中间页 **AI 导读**（`ai_summary_zh`，XML 注入）+ **原文官方链** + **AI 阅读** 外链，三者并列 |
| **范围** | **仅英文**；中文 CNKI/CMA **不提供 AI 阅读**（C15） |
| **实现** | `doubao_rpa.py` → `batch_worker.py` → XML/entries 注入（Route 2） |

---

### 讨论点 1：竞品到底是什么？

| **决议** | 不是「AI 解读信息流产品」，而是 **ima 共享 PDF 库 + 底部库级 RAG + 微信群推广** |
| **对 AES 含义** | 对标对象应改为 **「库级问答 + 社群拉新」**，而非「卡片化 AI 日报」 |

---

### 讨论点 2：AES 是否做 ima 式库级 RAG？

| Pro | ima 验证了「跨文献提问」需求 |
| Con | 需 mega 语料库；版权与 ima 同轨；与已定 **单篇豆包链** 方案重复且更重 |
| **决议** | **不做** ima 式库级 RAG；英文 AI 能力 = **单篇豆包分享链** + 中间页 **AI 导读** |
| **待观察** | 豆包链有效期、未登录用户能否只读、分享链二次传播范围 |

---

### 讨论点 3：微信群推广学不学？

| **决议** | **学渠道，不学内容** — 群可推 **标签精选 / 中间页 / 订阅链接**，**不推** PDF 包或全文库邀请 |
| **待决** | 是否开企业微信/个人号辅助入流（C23） |

---

### 讨论点 4：版权 — 我们与之的距离

| **决议** | AES **明确拒绝** 复刻「万篇全文共享库 + 公开公众号推广」模式 |
| **记录** | 该 ima 案例作为 **反面合规参照** 写入 C15 说明（可选） |

---

### 讨论点 5：腾讯是否在纵容？

| **讨论** | 平台提供能力 + 事后治理；**不能** 推断腾讯认可侵权 |
| **产品结论** | 依赖 ima 存 **未授权全文** = **平台政策 + 版权双风险**；AES 不押注此路径 |

---

### 讨论点 6：豆包链侵权风险是否可接受？

| **相对 ima** | **显著更低** — 无 mega 库、无库级 RAG、逐篇外链、中文不做 |
| **绝对** | **非零** — PDF 仍上传豆包、分享链可能扩散、规模累积仍有风险 |
| **决议（v1.3 建议）** | 有条件可接受 + §4.5 七条运营约束 |
| **决议（v1.4 已定）** | ✅ **培育期先用豆包链，接受已知风险** — 主因 **UX 流畅**；当前 **无收费盈利**；后续有更好的方法再迭代（§4.6） |
| **待办** | 豆包链访问控制实测；运行期记录投诉/失效；P2 评估替代方案 |

---

### 讨论点 7：更低风险路径（v1.6 修正）

| **零风险（AES 侧）** | **仅 DOI + 用户自备 PDF 上传 AI（D）** — 不是「低风险」，是 **零** |
| **非零但可迭代** | **微信私发 PDF（B）** — 培育期后唯一值得做的降档 |
| **搁置** | **方案 E**（代投用户豆包账号）— 基本不可行，不投资源 |
| **邮件** | 中低 + UX 差 — 备用 only |
| **张力** | **流畅（豆包链）↔ 零（DOI 自备）** — 培育期选前者；投诉/收紧时切 D |
| **长期脑洞** | 见 **§4.8** — Access Broker（Unpaywall/GetFTR/S2）为 **全球正途** |

---

### 讨论点 8：长期北极星 — Access Broker vs 豆包链（修正 · v1.8）

| **付费现实** | 多数 **新** 文献合法全文 = **用户自购** 或 **机构订阅**；OA 是 **少数** |
| **平台边界** | AES **不代付** PPV / DeepDyve；只 **链出 + 导读** |
| **Access Broker 价值** | 帮命中 **少数 OA** + 帮会用 **机构** 的用户 — **不能** 消灭付费墙 |
| **豆包链定位** | 培育期 UX 过渡 — 填「用户不愿付、平台不代付、仍要读」的洞 |
| **中间页** | 主路径 = **DOI 购买**；OA/机构/DeepDyve/豆包 **分轨展示**（§4.9） |

---

### 讨论点 9：平台不替用户付费（已定）

| **决议** | 合法要付费的新文献 **绕不开**；**平台不可能也不应代用户付费** |
| **产品承诺** | 卖 **筛选 + 导读 + 合法入口**；**不** 卖「免费全文库」 |
| **与 ima** | ima 用 **隐性免费** 换 UX；AES 用 **诚实分层** + 培育期豆包 |

## 9. 一句话总结

**ima 竞品** = 海量 PDF **共享库** + 列表点读原文 + 底部 **库级 RAG** + 微信群推广。  

**AES（v1.8）** = **导读 + 标签订阅** 为核心；合法全文 **用户自购或机构读**（平台 **不代付**）；培育期 **豆包链** 填 UX 洞；**不做** ima 免费万篇库。  

**错位关系**：ima 卖「整个库一起问」；AES 卖「这篇值得读，去豆包接着问」— **不是同一 AI 产品**。
